## Chest-UI / ChestFormData — CC BY 4.0

**Source:** https://github.com/Herobrine643928/Chest-UI
**Licence:** [Creative Commons Attribution 4.0 International](https://creativecommons.org/licenses/by/4.0/)
**Authors:** original pack by LeGend077; maintained by Herobrine64 and
LeGend077; pattern function by Aex66.

Admin+ uses this work to draw a player's inventory as a chest window instead of
a list of buttons. Bedrock gives scripts no container UI, so the technique
smuggles one through an ordinary form: a sentinel string in the title tells a
JSON-UI resource pack to redraw the form as a 9-column grid.

**Files derived from it, and how they were changed:**

| File | Change |
|---|---|
| `Admin+ BP/scripts/core/typeIds.js` | Used as-is. A data table of Minecraft item ids; only a header comment was added. |
| `Admin+ RP/ui/adminplus_ui.json` | Modified. Renamed from `mce_ui.json`; the UI namespace was renamed to `adminplus_ui` so two installed packs cannot collide on it; `chest_panel` was given explicit centre anchors. |
| `Admin+ RP/ui/server_form.json` | Modified. A dead `trade_form` control was removed (it inherited a vanilla namespace with no such member and logged an error every time any form opened); `$dialog_text_color` is now defined locally rather than through a global variables file; and the multi-line trigger was changed — see below. |

That file also carries a **multi-line form field** — a chain of controls ending
at Minecraft's own `npc_interact.multiline_text_edit_control`, the one the NPC
dialogue editor uses. Admin+ inherited it here and used it for the first time in
2.0.0, to make `/admin ▸ < Code >` an editable config file rather than a
one-line box. The upstream trigger is the *printable* title `JavaScript REPL`;
Admin+ uses a sentinel that renders as nothing (`§c§o§d§e`, the same style as
this project's own `§m§c§e`) and keeps the original working alongside it, so a
pack speaking the older protocol still renders correctly whichever one wins the
resource-pack order. The idea, and the working example, are theirs.

`Admin+ BP/scripts/core/chestUI.js` is **our own** implementation of the script
side. It deliberately speaks the same wire format — the same title sentinels,
the same icon encoding — because two packs that implement this protocol can then
render each other's windows correctly whichever one wins the resource-pack
order. Diverging would guarantee that exactly one of them looked broken.

Textures under `Admin+ RP/textures/ui/` (`shop_ui`, `small_ui`, `d_b`, `d_g`,
`form_bubble`) were **drawn for this project**, not taken from that pack.

Not used: that project's `_global_variables.json`, which repaints
`$dialog_text_color` for every dialog in the game from every installed pack.

## Techniques learned, code not taken

No files from these packs are included. They are credited because the ideas are
theirs and the work would have taken far longer without them.

**SafeGuard** — that a pack requiring a beta module cannot warn you when Beta
APIs is off, because its scripts never start. The answer is `.mcfunction` data,
which keeps running regardless. Admin+ builds its own watchdog on that idea in
`Admin+ BP/functions/`.

**UltraVanish** — that the invisibility effect does not hide armour or held
items, and that a resource-pack animation scaling every bone to zero does.
Admin+ has its own animation and its own script; what came from there is
knowing that the approach works, and that it must be re-applied every tick with
a real blend-out time or the armour flickers.

## Minecraft

`Admin+ BP/scripts/core/itemTextures.js` is generated by `tools/genicons.py`
from the vanilla resource packs of an installed copy of Minecraft. It contains
**texture paths only** — strings such as `textures/items/diamond_sword` — and no
